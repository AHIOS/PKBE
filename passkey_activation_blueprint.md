# Cross-Device App Activation via Passkey (WebAuthn Hybrid Flow)
## Technical Specification & Architecture Blueprint

This document specifies the technical design, logical flow, and multi-tier architecture for an enterprise-grade cross-device application activation SDK and backend system. The core goal is to securely transfer an application's activation state from an active authenticated device (**Device A**) to a new unauthenticated device (**Device B**) using Apple/Google native **FIDO Hybrid (Proximity) Passkey** verification and asynchronous cloud messaging.

---

## 1. Functional Perspective

The objective is to provide a zero-password, highly secure cross-device onboarding journey.

### User Journey Flow
1. **Initiation:** The user opens the newly downloaded app on **Device B** and taps "Activate via Existing Device".
2. **Challenge Presentation:** Device B connects to the backend, registers its intent, and displays a standard system-driven Passkey/FIDO QR code sheet on the screen.
3. **Proximity Check & Scanning:** The user holds **Device A** (already active) up to scan Device B's screen. The operating systems natively establish an encrypted local Bluetooth Low Energy (BLE) link to prove physical proximity.
4. **Biometric Authorization:** Device A prompts the user for local biometrics (Face ID/Touch ID or Fingerprint). Upon success, Device A cryptographically signs the WebAuthn challenge.
5. **Auto-Activation:** Device A transparently transmits the cryptographic signature back to the server through the secure FIDO routing channel. Device B automatically unlocks and transitions to an authenticated state without user manual data entry.

## 2. Logical Perspective

The system operates across three separate lifecycle spaces: Passkey Registration, Session Setup, and Handoff Verification.

```
[Device B (New)]                          [Spring Backend]                     [Device A (Active)]
       |                                         |                                      |
       |-- 1. POST /activation/initiate ------->|                                      |
       |<- 2. Returns SessionID & Challenge -----|                                      |
       |                                         |                                      |
       | [Local Debug ONLY]                      |                                      |
       |-- 3. Opens SSE Connection ------------->|                                      |
       |                                         |                                      |
       |-- 4. Triggers System Hybrid UI Sheet --|                                      |
       |      (Displays FIDO Universal QR)       |                                      |
       |                                         |                                      |
       |================== 5. Native OS Proximity BLE Tunnel Matrix ===================|
       |                                         |                                      |
       |                                         |<-- 6. POST /activation/verify -------|
       |                                         |    (Submits WebAuthn Signature)      |
       |                                         |                                      |
       |                                         |-- 7. Validates Signature ------------|
       |                                         |-- 8. Fetches Target Token -----------|
       |                                         |-- 9. Generates Ecosystem Payload ----|
       |                                         |                                      |
       |<- 10. Emits SSE [Local Debug Profile] --|                                      |
       |                  OR                     |                                      |
       |<=[10. Pushes FCM Notification (GCP)]====|======================================|
```

### Protocol Invariants
* **CTAP2 & WebAuthn Encapsulation:** To secure cross-platform stability, mobile operating systems explicitly block third-party applications from reading or writing raw CTAP2 Bluetooth channels. The SDKs must rely exclusively on native platform wrappers (`AuthenticationServices` on iOS, `CredentialManager` on Android) which abstract the hybrid QR and BLE matrix automatically.
* **Cryptographic Bindings:** Every activation request requires a cryptographic challenge generated by the backend with a short Time-To-Live (TTL <= 120s). The user signature collected from Device A must explicitly lock against this ephemeral challenge, preventing replay and session interception attacks.

## 3. Architectural Perspective

To support a seamless Developer Experience (DX) alongside a high-throughput, cloud-native deployment on **Google Cloud Platform (GCP)**, the platform follows a **Hexagonal Architecture (Ports and Adapters)** pattern.

### Structural decoupling: Local vs. Production
The core application relies on abstract interfaces. By toggling Spring Profiles (`local` vs `gcp`), the execution engine swaps out underlying dependencies seamlessly.

| Component Component | Local Profile (`local`) | Cloud Profile (`gcp`) | Purpose |
| :--- | :--- | :--- | :--- |
| **Ephemeral Session Store** | In-Memory `ConcurrentHashMap` | Google Cloud Firestore (Datastore Mode) | Caches active challenges and device routing destinations. Auto-purged via Datastore TTL. |
| **Notification Engine** | Server-Sent Events (SSE) `SseEmitter` | Firebase Cloud Messaging (FCM) | Relays the downstream encrypted application state token back to Device B. |
| **Credential Directory** | Local H2 Database | GCP Cloud SQL / Cloud Spanner | Stores permanent user cryptographic public keys generated during initial registration. |

### Architectural Decoupling Benefits
* **No Network Boundary Issues:** Using production-tier FCM pushes removes the overhead of orchestrating persistent long-lived WebSockets or SSE pipes across auto-scaling Google Kubernetes Engine (GKE) or Cloud Run container pods, bypassing HTTP/1.1 load balancer timeout closures.
* **Self-Contained Local Debugging:** Engineers can validate the entire client-to-server interaction loop completely offline on their workstation without requiring GCP project IAM access, Docker instances, or active internet routing profiles.

## 4. API & Layer Contracts

### Core Interface Port Definitions (Spring Backend)

```java
public interface EphemeralSessionStore {
    void saveSession(String sessionId, String challenge, String clientTransportToken, long ttlInSeconds);
    Optional<ActivationSessionData> getSession(String sessionId);
    void invalidateSession(String sessionId);
}

public interface ActivationNotificationService {
    void registerListener(String sessionId, Object transportObject); // Used for Local SSE Emitters
    void sendActivationPayload(String targetIdentifier, String encryptedPayload); // Dispatches to SSE or FCM
}
```

### Symmetrical Mobile SDK Interface Contracts

To simplify integration for application feature developers, both the iOS (`.xcframework`) and Android libraries expose matching object topologies:

#### Phase 1: Key Registration (Device A Initial Configuration)
* **iOS (`PasskeyRegistrationManager`):**
  ```swift
  public func createPasskey(optionsJson: String, presentingWindow: UIWindow) async throws -> String
  ```
* **Android (`PasskeyRegistrationManager`):**
  ```kotlin
  suspend fun createPasskey(optionsJson: String): String
  ```

#### Phase 2: Cross-Device Handoff Initiation (Device B Core Execution)
* **iOS (`PasskeyActivationManager`):**
  ```swift
  public func performHybridHandoff(challenge: String, rpId: String) async throws -> Void
  ```
* **Android (`PasskeyActivationManager`):**
  ```kotlin
  suspend fun performHybridHandoff(challengeBase64: String, rpId: String): Unit
  ```

## 5. Security & Infra Hardening Guide

1. **Domain Assertions (AASA & AssetLinks):** To allow the operating systems to invoke platform passkeys, the backend domain must actively prove identity tracking.
   * **iOS:** Host a valid Apple App Site Association declaration at `https://yourdomain.com/.well-known/apple-app-site-association` linking your exact Apple Team App ID.
   * **Android:** Host a valid Digital Asset Links array file at `https://yourdomain.com/.well-known/assetlinks.json` defining your package signature fingerprints.
2. **Zero-Knowledge Target Payloads:** The activation token sent through the downstream communication handler (FCM/SSE) should be cryptographically encrypted end-to-end. Device B generates an ephemeral keypair upon initialization, exports the public component inside the `/activation/initiate` REST envelope, and keeps the private component securely sequestered in local memory to decrypt the server's final payload response.
